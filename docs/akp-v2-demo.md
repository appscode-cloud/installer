# AKP v2 demo: the ace chart in `v2_only`, on a single-node k3s

AKP v2 is AKP (b3) running `[iam] MODE = v2_only`, with **iam** (Casdoor embedded as the identity provider), platform-ui and
cluster-ui as the frontends, routed through the Gateway of **Voyager Gateway** (Envoy Gateway based, no Traefik), NATS in
**operator mode**, and sign-in only on Casdoor's hosted pages. It is the AKP product line: no Trust Console, no KubePatch.

This is the **`ace` chart** with `ProductLine: AKP` and `global.akp.mode: v2_only` (PR #1430), plus what ace does not make.

## Design choice

| Piece | Where it comes from |
|---|---|
| b3 (`platform-api`), platform-ui, cluster-ui, Grafana, Perses, Cadence, NATS, the Gateway and its routes | the `ace` chart and its sub-charts, values in `charts/ace/profiles/akp-v2-demo.yaml` |
| Postgres 18, Casdoor (one organization, one application), the NATS operator/system/admin identities, the Gateway certificate | `charts/akp-prereqs` (a separate release, installed first, same namespace) |
| the credentials as ace values (database password, Casdoor client secret, KMS key, NATS identities, NATS server operator config) | `hack/akp-v2-demo/ace-values.sh`, a values file that is never printed (mode 0600) |
| Voyager Gateway (controller, GatewayClass `ace`, EnvoyProxy) | `hack/akp-v2-demo/install.sh gateway`; k3s keeps its own Gateway API CRDs |
| images | `hack/akp-v2-demo/load-images.sh` (b3, platform-ui, cluster-ui are built; Casdoor, Postgres, NATS are pulled) |

Why a separate `akp-prereqs` release and not a sub-chart of ace: ace takes the NATS identities and the Casdoor client secret as
**values** (`settings.nats.*`, `settings.iam.casdoor.clientSecret`, the NATS server's operator JWT), so they must exist before
ace is rendered; a sub-chart's hook Job runs after the render. ace also expects KubeDB, KubeStash, cert-manager and lib-selfhost
to make the database, the cache, the certificate and those credentials; on a cluster without them `akp-prereqs` plays that part.

The branch is stacked on `product-line` (#1430): the new work is only what a v2_only AKP needs on top of it.

## What was added to ace beyond #1430

Default renders are unchanged: `helm template` of `charts/ace` with default values and with `ace.sample.yaml` are byte for byte
the same before and after (checked with the random secrets masked).

ace chart:

- `disableFeatures` (list, default empty): leaves out ace's own templates by feature name (`db`, `cache`, `clusterBackup`,
  `cleaner`, `consoleImporter`, `grafanaConfig`, `cadence`, `setupJob`) in any product line. `db` is new: the KubeDB Postgres,
  Pgpool, archiver, backup and init-script templates.
- `settings.db.host`: a Postgres that is not ace's KubeDB one (host:port).
- `settings.iam.casdoor.publicUrl`: `[iam] CASDOOR_PUBLIC_URL`, Casdoor as the browser reaches it (the hosted sign-in redirect).
- Gateway routes: `<settings.iam.publicPath>` (`/iam`, iam's hosted `/casdoor/login` and `/casdoor/callback`) goes to b3 in
  `dual` and `v2_only`; in `v2_only` the home route redirects `/` to `/id/` (there is no `/accounts/selfhost-home`).
- the setup Job is not rendered in `v2_only` (the same steps are init containers of the API pod, see below), and the
  setup config leaves out `syncPersesAccounts` there (`b3 dev` would read `ac_user`).
- the Grafana config uses Grafana's own database for its remote cache and an in-memory session when the `cache` feature is off.

platform-api chart:

- `v2_only` (read from `global.akp.mode`): the probes are an exec `curl` of the Connect call
  `akp.branding.v2.BrandingService/GetBranding` (b3 serves neither `/healthz` nor `/api/v1/version` there), and the init
  containers are b3's order for a fresh install: `b3 migrate`, `b3 dev --setup-config` (records the NATS accounts),
  `b3 admin iam-bootstrap-admin` (the first site administrator).
- `iam.bootstrapAdmin.*`, `settings.secretName.setupConfig`, `extraInitContainers` (runs before the chart's own).

Go types for the new values are in `apis/installer/v1`; schemas and READMEs are regenerated by `make gen`.

## Run it

On a build host (docker, an ssh agent that can read the private repositories) build and import the images; on the k3s host
install. Pick a name that is not a public suffix (`akp.appscode.test`, not `*.nip.io`: b3 sets cookies for the last two labels
of the host and browsers may refuse `Domain=nip.io`). Put it in `/etc/hosts` on the machines whose browser you use:

```
10.2.0.73  akp.appscode.test casdoor.akp.appscode.test
```

```sh
# build host
TARGET=ubuntu@10.2.0.73 hack/akp-v2-demo/load-images.sh all
# k3s host, from a checkout (or a copy of charts/ and hack/akp-v2-demo/)
hack/akp-v2-demo/install.sh all          # gateway, prereqs, ace
```

`HOST=<name> hack/akp-v2-demo/install.sh ...` uses another name; then change it in `charts/ace/profiles/akp-v2-demo.yaml` and
`hack/akp-v2-demo/prereqs-values.yaml` too (the Casdoor URL and the sign-in URL are in the profile).
By IP: `curl -k --resolve akp.appscode.test:443:10.2.0.73 https://akp.appscode.test/...` (or `-H 'Host: ...'`).

The first site administrator is `admin`; its password is in Secret `akp-prereqs-credentials` (key `admin-password`) and is the
password of the Casdoor user `admin`. Other Secrets: `akp-prereqs-nats-creds` (the NATS identities), `ace-gw-cert`.

Order in a fresh install matters in one place: Grafana and Perses create their tables in b3's database (`org`, `user`,
`perses_users`, ...), and b3 writes the first administrator to them **only if they exist** (in `v2_only` nothing syncs them
later: `b3 dev --sync-grafana-users` reads `ac_user`). The platform-api pod therefore waits for those tables
(`extraInitContainers` in the profile) before `iam-bootstrap-admin`. Without it, `CreateOrganization` fails with
`pq: relation "org" does not exist` (Grafana not started yet) or `user does not exist [... name: admin ...]` (administrator made
before Grafana). This is the answer to the `org does not exist` the Trust Console builds hit: it is not the site organization step
(`b3 dev` in `v2_only` makes none).

## Findings (what does not work, or is not b3's yet)

- **CSRF cookie name.** iam's hosted sign-in sets `iam_csrf`; platform-ui, cluster-ui and ui-modules (`akp-v2-iam`) read `_csrf` for
  `X-Csrf-Token`. After a completed sign-in every AKP v2 call answers `missing or invalid CSRF token` and the UI loops back to
  sign-in. The demo b3 image carries a one-line patch (`hack/akp-v2-demo/b3-csrf-cookie.patch`, `CSRFCookie: "_csrf"`, tag
  suffix `-csrf`); the right fix is in b3 or the UIs, not here.
- `b3 dev --sync-grafana-users` and the cluster-import task read `ac_user`, which `v2_only` does not have: **ImportCluster registers
  the cluster (provider Generic, with a kubeconfig; endpoint, version, nodes are read) but its install task fails** with
  `pq: relation "ac_user" does not exist`. ValidateImport and CreateOrganization work. Import also needs Cadence and `components.fluxCd: true`.
- UIs call `GET /api/v1/user/settings/pagination`, which `v2_only` does not serve (404, harmless).
- `[storage] BUCKET_URL` is still `gs://ace-data` (ace's default); b3 logs it and keeps going.
- Adding Grafana by `helm upgrade` to an existing release: ace writes `skip_migrations = true` on upgrade, so Grafana does not make
  its tables. Install it from the start (as `install.sh` does).
- A change of `[iam]` or `[cadence]` in the config Secret does not restart b3: `kubectl delete pod <release>-platform-api-0`.
- `charts/akp-prereqs`: one Postgres pod, a self-signed certificate, generated credentials. Not for production.

## Teardown

`hack/akp-v2-demo/teardown.sh --yes` on the k3s host (without `--yes` it prints what it would remove). It removes both releases,
the PVCs, the Secrets Helm does not own, Voyager Gateway and its cluster-scoped objects, and the imported images. k3s' Gateway API
CRDs stay.
